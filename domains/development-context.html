    Development & Context¶

    Primary sources: PostgreSQL event and demolition tables; CSV files; crime data from PostgreSQL; construction cost estimates; REMI price index forecasts

    This domain brings together four related categories:

    • Planned development events — specific buildings that will be added or removed at known future years, plus background demolition rates
    • Neighborhood context — school quality and crime rates that influence location choice
    • Building construction costs — per-square-foot construction cost estimates by building type and area, which determine feasibility of new development
    • Price growth rates — REMI-derived annual PCE inflation applied to construction costs each simulation year (property-value appreciation is a separate, large-area-specific personal-income series documented under Demographics)

    All three categories shape where and how much development and population locate in the model.

    Development Events¶

    Key distinction between event tables:

    • events_addition / events_deletion are real estate events — they add or remove physical buildings in the simulation. Use these for known construction projects or planned demolitions where the structure itself is changing.
    • refiner_events is an agent-level event — it adds or removes jobs, households, or group quarters persons at targeted locations without changing the building inventory. Use this for planned employment relocations, major employer openings or closings, facility population changes, and other events that affect who occupies buildings rather than what buildings exist.

    Event timing is by year, not date. Every event's timing is a single integer year — year_built on events_addition, year_demo on events_deletion (renamed to year_built on load), and the year column on refiner_events. There is no calendar date anywhere in the chain: the source tables carry only the year column, the input SQL pulls only that year column, and the model fires an event in the year whose value equals the current simulation year (year_built == iter_var in the scheduled add/demolish steps; refinements.year == year in the refiner).

    What this means for developing event tables: all events sharing a year are applied together — there is no within-year ordering, sequencing, or partial-year timing. When curating event records, only the year matters; a month or day has no effect on when (or whether) an event fires. Assign each event to the year it should take effect and do not attempt to encode sub-year dates — they are neither stored nor read.

    Base-year event cutoff¶

    The input build assembles buildings as the base-year snapshot from the preceding building GIS view plus the two physical-event tables. It first removes deletion events dated in the base year, then appends addition events dated in the base year. For the current cycle, the complete 2024 building view plus complete 2025 additions and deletions produces the 2025 buildings snapshot.

    This gives a clear acceptance rule for the base inventory: it is complete when the preceding-year GIS building view is complete and every physical addition and deletion for the base year has been entered. Event records after the base year stay in their event tables. They can be added, corrected, or dropped without rebuilding the current base-year buildings snapshot; the forecast captures them when it reaches their year.

    Do not also place a future event directly in buildings, because that would cause the physical change to be represented twice. Conversely, do not omit a base-year event from the assembly run, because the base snapshot would be stale.

    events_addition¶

    Known physical building additions, such as planned developments, stadiums, and hospitals. A row dated in the base year is incorporated into the assembled buildings snapshot. A row dated after the base year remains a scheduled forecast input and adds a building when its year is reached.

    Index: objectid (unique)

    Column Type Rules Notes
    objectid int unique, no null Index
    parcel_id int32 no null Must exist in parcels
    building_type_id int8 join → building_types, no null
    year_built int16 base year or later, no null Year the building is added
    residential_units int16 no null 0 for non-residential
    non_residential_sqft int32 no null 0 for residential
    stories int —
    gqcap int ≥ 0, no null Facility group-quarters capacity; 0 means the event does not create a GQ facility
    event_id int unique, no null Stable event identifier. Retain it across input refreshes; refiner_events may use it to target the resulting event building.
    building_id int — Optional source-system building reference. It is not the identifier assigned to the event-created building in forecast outputs.

    For an event that creates a GQ facility, set gqcap to the number of beds. Do not infer GQ capacity from building_type_id; use 0 when the event does not create a GQ facility.

    Common issues: - parcel_id not in parcels — building can't be placed; fix parcel reference - a base-year row missing from the assembly run — the base buildings snapshot will be incomplete - year_built before the base year — verify the forecast-cycle cutoff and source record

    events_deletion¶

    Known physical building deletions or demolitions. A row dated in the base year removes the building while the base snapshot is assembled. A row dated after the base year remains a scheduled forecast input and removes the building when its year is reached.

    Index: objectid (unique)

    Column Type Rules Notes
    objectid int unique, no null
    building_id int32 no null Building to be demolished
    year_built int16 base year or later, no null Year of demolition. The source field is year_demo; it is normalized to year_built in the model-input HDF.

    Common issues: - building_id not in buildings — skipped but should be cleaned up - a base-year demolition missing from the assembly run — the base buildings snapshot will be stale - Demolition year before the base year — verify the forecast-cycle cutoff and source record

    refiner_events¶

    Agent-level events collected from various sources. Unlike events_addition/events_deletion, this table does not change the building inventory — it adds or removes agents (jobs, households, or group quarters persons) at specific locations. Typical uses include planned major employer openings or relocations, GQ facility population changes, and other future occupancy events that do not involve new construction or demolition. Assembled by merging employment events and GQ events CSVs.

    Index: refinement_id (unique, int16)

    Column Type Rules Notes
    refinement_id int16 unique, no null
    transaction_id int16 no null Groups related events (e.g., a move = one remove + one add)
    year int16 forecast year range, no null
    action object "add" or "remove"
    agents object "jobs", "households", or "group_quarters" Which agent type to affect
    agent_expression object no null Pandas query string filtering the agent table
    location_expression object no null Pandas query string filtering the buildings table
    amount int16 no null Number of agents to add or remove

    agent_expression and location_expression syntax: Both are pandas query strings applied at runtime to the relevant DataFrame. agent_expression filters the agents table (e.g., jobs, households); location_expression filters the buildings table.

    Examples from the current data:

    action agents agent_expression location_expression amount Meaning
    add jobs sector_id==6 event_id==9042132 250 Add 250 retail jobs to the event building with id 9042132
    add jobs sector_id==3 building_id==8901277 1700 Add 1700 manufacturing jobs to a specific building
    remove jobs sector_id==9 city_id==501 500 Remove 500 service jobs from buildings in city 501

    The event_id column in events_addition is the same as the event_id value used in location_expression — this is how a refiner event targets a planned new building.

    Synchronization principles¶

    refiner_events changes occupancy, while the base-year buildings, events_addition, and events_deletion tables define which buildings exist. They therefore need to describe one consistent forecast-input release.

    • A location expression using event_id==... must use the immutable events_addition.event_id, not the optional source-system building_id. Base-year buildings begin with event_id = 0; an event ID becomes available on a building only when its scheduled addition has been processed. The scheduled-development step runs before the refiner step in each forecast year (models.py:2697; simulation_2055.py:98).
    • A refiner event for a planned building cannot take effect before that building's year_built. Its effective year must be the same as or later than the corresponding scheduled-addition year.
    • A location expression using building_id==... must reference a building in the assembled base-year buildings table. Do not assume that the optional source-system building_id on an addition will be the runtime ID of the building created during the forecast.
    • A building targeted by a refiner event must not be removed by events_deletion in the same or an earlier forecast year. Scheduled demolitions are applied before the refiner step, so the target building would no longer be available.
    • Base-year additions and deletions must already be reflected in the assembled buildings snapshot. Refiner records dated at or before the base year need to be reconciled with that snapshot rather than treated as future events.

    These principles are about consistency between the related inputs; they apply regardless of which team maintains each source table.

    Update: Add rows to the employment events CSV for new employment centers or relocations. Add rows to the GQ events CSV for GQ facility changes. Merge both into refiner_events via the build pipeline.

    demolition_rates¶

    Annual background demolition counts by city and building type. Applied probabilistically each year by random_demolition_events.

    Index: city_id

    Column Type Notes
    city_id int16 MCD reference (= semmcd outside Detroit)
    type81units int32 Single-family units to demolish annually
    type82units int32 Attached condo units
    type83units int32 Multi-family units
    type84units int32 Mobile home units
    typenonsqft int32 Non-residential sq ft to demolish annually

    These are absolute counts (not rates) applied stochastically — buildings are sampled to meet each city's annual target.

    Common issues: - Cities with null values are treated as 0 demolitions — verify that zero is intentional vs. missing data - Update in PostgreSQL when calibrating to new demolition patterns

    landmark_worksites¶

    Major employers whose jobs are protected from simulation randomness. Large factories, university campuses, hospital complexes.

    Column Notes
    building_id Building to protect — receives sp_filter = -1 at startup

    How it works: Buildings in this list get sp_filter = -1 at startup, preventing the ELCM and relocation models from removing their jobs.

    Update: Add new anchor employers when major facilities open; remove entries if a facility closes. Keep the list conservative — over-protecting buildings reduces model responsiveness.

    Common issues: - building_id values that no longer exist in buildings — these are silently skipped but should be removed

    Neighborhood Context¶

    schools¶

    K-12 school locations and quality scores. Used as HLCM features — school quality affects where families with children choose to live.

    Index: bcode (unique)

    Column Type Rules Notes
    bcode int16 unique, no null School building code
    bname object — School name
    dcode int32 range [47010–84060], no null School district code
    gradelist object no null Grade levels served
    is_grade_school int8 values: 0, 1 1=K-8
    point_x float64 no null State plane X coordinate
    point_y float64 no null State plane Y coordinate
    totalachievementindex float64 no null School achievement score
    TOTAL_ENROLLMENT float32 may be null Total enrollment (single value, all grades)
    zone_id int no null TAZ the school falls in
    maz_id int no null MAZ the school falls in

    Update: Refresh from the Michigan Department of Education database when new schools open, schools close, or achievement scores are updated. For new schools without a score, use the district average.

    Common issues: - Coordinates outside the 7-county region — verify data - totalachievementindex = null — causes null neighborhood variables in HLCM; fill with district average

    Travel-model enrollment use (TAZ/MAZ zonal inputs, forecast_outputs/travel_model/): this table is the base-year enrollment source. Two limitations are handled downstream and should be understood:

    • Single TOTAL_ENROLLMENT, no grade split. The travel-model pipeline splits it into k-8 vs 9-12 in proportion to the number of grades each school serves (from gradelist). This assumes ~equal enrollment per grade, so it under-weights 9-12 relative to actual grade-level counts (a K-12 school sends 9/13 to k-8, 4/13 to 9-12). Providing measured grades_1_8_enrollment / grades_9_12_enrollment would remove the approximation.
    • dcode is not re-keyed to parcels.school_id. Only ~110 of the 128 population school districts overlap the ~536 dcodes here (≈23% of enrollment sits in non-matching codes). The enrollment step scales base enrollment by a per-district population ratio; districts with no population match carry base enrollment unscaled (scale = 1.0) rather than being dropped. Re-keying dcode to the parcels.school_id coding (25030–82430) would let every district be population-scaled.
    • 321 schools have null TOTAL_ENROLLMENT (counted as 0).

    crime_rates¶

    Violent and property crime rates by parcel. Derived from city-level crime data — all parcels in a city receive the same rate.

    Index: parcel_id (unique, joins to parcels)

    Column Type Rules Notes
    parcel_id int32 join → parcels, no null Index
    ucr_crime_rate float64 no null Violent crime rate (UCR)
    other_crime_rate float64 no null Property crime rate

    Update: Update the crime rates table in PostgreSQL with new annual data by city. The parcel-level values are derived automatically from city rates when the SQL query runs.

    Common issues: - Cities with no crime data result in null rates — null values cause model errors; fill with regional average

    Building Construction Costs¶

    Construction cost estimates drive the developer model's feasibility analysis (proforma). The model evaluates whether building new structures is financially viable by comparing expected revenue (from real estate price models) against estimated construction costs. If cost exceeds revenue, no new construction occurs in that location.

    What Is Required¶

    For each developable building type, the model needs a per-square-foot construction cost differentiated by building form, story count, and geographic pricing area. Three pricing areas are defined to reflect local construction market differences across the region.

    The developable building types and their general forms are:

    Building type IDs General Form
    81 Single-family residential
    82 Attached condo
    83 Multi-family apartment
    21, 65 Retail / restaurant
    23 Office
    31 Manufacturing
    32 Wholesale
    33 Warehouse
    51 Medical office
    52 Hospital
    53 Residential care
    61, 91 Leisure / entertainment
    63 Hotel

    Building types without a cost mapping (institutional, governmental, agricultural, etc.) are not modeled as developable.

    Source Data¶

    Cost estimates are sourced from a construction cost estimating service, providing per-square-foot costs by building form, story count, and pricing area. The resulting summary table maps each building type to its construction cost per square foot by pricing area.

    Update Procedure¶

    1. Obtain updated square foot cost estimates for the building forms listed above, for each pricing area.
    2. Map each building form to the corresponding building_type_id codes using the building types lookup file.
    3. Produce a summary cost table and coordinate with the modeling team to incorporate the updated costs into the proforma configuration.

    Common issues: - Building types missing from the cost table will have zero construction cost — the model will treat them as infinitely profitable; verify all developable types are covered - Large cost differences between pricing areas should be reviewed for plausibility

    remi_pce_growth_rate¶

    Annual PCE (Personal Consumption Expenditure) price index growth rate for the region, by forecast year. PCE is a standard measure of economy-wide price change — think of it as the REMI-projected inflation rate for the Southeast Michigan economy. The simulation uses it in exactly one place: cost_shifter_callback in models.py, which inflates new-construction costs forward from the base year before the proforma feasibility calculation. It does not drive property-value appreciation — that's a separate series (remi_pi_growth_rates, personal income, computed per large area) consumed by increase_property_values. An earlier version of this page conflated the two; it doesn't.

    Structure: One row per forecast year

    Column Type Notes
    year int16 Forecast year — index
    pce_growth_rate float64 Annual growth rate as a fraction (e.g., 0.023 = 2.3%); applied cumulatively — each year's cost compounds the previous

    A rate of 0.0 means no price change that year. The simulation falls back to a default rate (currently 2.0%) for any year missing from this table, so missing years do not crash the model but will produce incorrect results.

    Why region-wide, not per-large-area: REMI's PCE index actually varies by large area (it isn't a true national constant despite being labeled "(Nation)" in the source workbooks). It's deliberately collapsed to one region-wide number here because the base construction-cost table is only differentiated by 3 pricing areas (AA/DET/ROAK), not REMI's 8 large areas — a per-large-area rate would be false precision the cost basis was never built to support.

    Produced by: forecast_data_input/development_context/PCE_growth_rate.py. Reads the "PCE-Price Index" row (summary sheet) from each of the 8 large-area SEMCOG Region {horizon} Preliminary Forecast workbooks, log-linear interpolates through the years REMI only reports in 5-year steps (it's annual through 2030, then 5-year jumps), combines the 8 series into one using household-population weights from remi_hh_pop, and converts to year-over-year growth rates. See that script's README.md for the full rationale. This is a different, newer REMI export than the one behind income_growth_rates (Demographics) — they are not regenerated together.

    Update: Re-run PCE_growth_rate.py whenever a new REMI preliminary-forecast vintage is delivered (update the 8 workbook paths if the vintage folder name changes), and whenever the forecast horizon extends (e.g., past 2055).

    Common issues: - Year range must cover all forecast years; missing years silently fall back to the 2.0% default — verify full coverage - Rates above 5% or below 0% are unusual and should be reviewed against REMI documentation before use - The 8 source workbooks report annual data only through 2030; years beyond that are interpolated, not REMI-native — re-check the interpolation if REMI delivers a fully annual series in a future vintage
